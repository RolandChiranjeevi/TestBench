# Test Plan: Decathlon & Heptathlon release readiness (AUD-20261109-01)

Identifiers and values follow `.claude/references/audit-contract.md` (contract 1.3).

## Scope
Black-box release-readiness check of the Decathlon & Heptathlon app: main flows, scoring accuracy, data handling, accessibility and layout, reporting what blocks a release.

Target http://localhost:8080 (local, build unknown). Requirements REQ-LOCAL-001 to REQ-LOCAL-012. Check types: Functional, Validation, State, Accessibility, Responsive, Visual. Viewports 1280x800, 768x1024, 375x812, light and dark. State changes only inside TP-Auditors (Decathlon) and TP-Auditors-H (Heptathlon); General is view-only.

Scope change 2026-11-09T12:38:40Z (confirmed by the user): the app cannot create a Mixed competition, so two TP competitions are used instead of one. See manifest limitations.

## Out of scope
- Load and performance testing
- Security testing beyond input handling
- Browsers other than Chromium
- Calling the API directly
- Any environment other than local
- The General competition (view only)

## Assumptions
- Points follow the World Athletics combined-events tables (rounded down); jumps are entered in cm, throws in m, times in s or m:ss, as the app's /api/events states.
- A result equal to the world record is valid; only a better one is impossible.
- Duplicate competitor names are allowed (user decision); a decimal comma is accepted (user decision).
- Plan items run in order (TPI-001 first, then the scoring athletes TPI-016 to TPI-019 before the items that depend on them); later items reuse data created earlier, as their preconditions state.

| REQ-LOCAL-005 | Standings are ordered and interactive | local | ready | Rows are sorted by total, highest first. Equal totals share a position. The count on each tab equals the number of rows in it. Clicking a row loads that competitor into 'Enter result'. |

| REQ-LOCAL-012 | The app is robust in normal use | local | ready | No console errors and no unexpected 4xx/5xx responses during normal flows. Rejected input shows a message instead of an unhandled error. |

## Heuristics used
- CRUD and data lifecycle; Follow the Data (create, read, update and delete of competitors and results; reload and export/import round-trips).
- Validation and input handling; Boundary Analysis (Goldilocks) at the world-record and max limits; Data Type Attacks: Strings (HTML characters, long strings, blanks) and Numbers (negative, non-numeric, decimal separator).
- Count: 0, 1, Many; Position: Beginning, Middle, End (sort order, ties); Sequences and State (re-saving an event, rename and back).
- Responsiveness and layout; Accessibility (A11Y) web patterns; Visual consistency.
- Quicktests: console errors and failed requests during every flow.

## Coverage gaps
- **CG-001** (REQ-LOCAL-010): No automated accessibility scan (axe) is run: axe-core is not installed and loading it was not approved. Issues an automated scan would find may be missed.
- **CG-002** (REQ-LOCAL-010): Screen reader output is not verified: no assistive technology is used. Only the accessibility tree and live-region markup are checked.
- **CG-003** (REQ-LOCAL-006): Mixed (typeless) named competitions are not tested: the app only creates Decathlon or Heptathlon competitions, and only General holds both. Holding both disciplines in one list is not verified.
- **CG-004** (REQ-LOCAL-006): Deleting a competition is not tested: the UI offers no delete action. TP-Auditors and TP-Auditors-H will be emptied instead of deleted.
- **CG-005** (REQ-LOCAL-004): Scoring is checked on a sample of values (one or two per event), not across the whole points table. Hand timing and other rule variants are not covered.
- **CG-006** (REQ-LOCAL-012): Behaviour when the server fails (5xx, timeouts) is not tested: forcing server errors is out of scope.
- **CG-007** (REQ-LOCAL-011): Visual design is not compared with a reference: none exists. Only clear defects (overflow, overlap, cut-off) are judged.
- **CG-008** (REQ-LOCAL-012): Only Chromium is tested: other browsers are out of scope.
